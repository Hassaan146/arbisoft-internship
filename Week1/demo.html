01

What the App Is

A single-page application (SPA): the browser loads one HTML page exactly once, then JavaScript swaps the visible content as you navigate — no full page reloads, no server round-trips per navigation.

It has four screens (Home, About, Reviews, Contact) that share one continuously-playing cinematic flower video as the background. The landing page is a pixel-faithful replica of the reference design; the other three pages use glassmorphism — frosted, semi-transparent panels floating over that same live video.

The defining characteristic: a single flower video plays behind everything, and glass panels float over it on inner pages. The entire visual identity depends on that video working correctly — which is why its playback reliability was engineered carefully.

The Stack

Vite builds it, React renders it, React Router routes it, and a quality layer (ESLint + Prettier + Vitest) keeps it clean and correct.

Build / Dev Server
Vite
Hot-reload dev server; bundles for production. Much faster than CRA (which is deprecated).
UI Library
React 18
Builds the screen from reusable components. Component reuse, huge ecosystem, the SPA standard.
Navigation
React Router v6
Maps URLs to screens, client-side. Intercepts link clicks, changes the URL, renders matching component.
Background
HTML5 <video>
The self-hosted flower clip, autoplay + loop. No CDN dependency, no CORS issues.
Particles
Canvas 2D
Drifting dots over the hero on the landing page. Native browser API, zero dependencies.
Styling
Plain CSS
Theme tokens + glassmorphism. No framework overhead, full control over every pixel.
Linting
ESLint (flat config)
Bug-catching + code rules. ESLint 9's new flat config format — an array of config objects.
Formatting
Prettier
Consistent code style. Owns formatting completely so ESLint can focus on correctness.
Testing
Vitest + Testing Library
Unit tests in a simulated DOM (jsdom). Vite-native runner, very fast.

The "Virtual Environment"

Node has no venv like Python. The isolated environment is the project folder itself. npm install reads package.json and downloads dependencies into a local node_modules/ that belongs only to this project — not globally.

FileRole
package.jsonManifest: lists dependencies + npm scripts. The source of truth.
package-lock.jsonPins exact versions for reproducible installs across machines.
node_modules/The downloaded libraries. Git-ignored; recreated by npm install.
04

How the App Boots — Render Pipeline

The browser only loads index.html once. Everything after that is JavaScript swapping components in and out.

1
index.html
The ONE page the browser ever loads. Contains <div id="root"> — an empty mount point. Also loads fonts and the JS entry point.
2
src/main.jsx — Ignition
Boots React and the Router. Wraps everything in React.StrictMode (dev-only safety checks) and BrowserRouter (enables URL routing). Mounts <App /> into #root.
3
src/App.jsx — Switchboard
The route table. Maps every URL to a screen. Picks a component by URL and React swaps it in with no server round-trip. This is the SPA.
4
Pages & Components — Render
<Landing /> for /. <Layout /> wraps About, Reviews, Contact. Layout provides the shared video background, navbar, footer, and an <Outlet /> slot where the current page renders.
05

Routing — The Two-Layout Strategy

There are two fundamentally different kinds of page, so there are two layouts:

Landing (/) stands alone. A full-bleed, immersive replica with its own fixed navbar, video container, particles, and scroll choreography. Not wrapped in the shared layout. It's the flagship experience — unique, self-contained.
About / Reviews / Contact share <Layout />. A common wrapper providing the shared video background, dark scrim overlay, glass navbar, footer, and an <Outlet /> — the slot where React Router injects the current page's content.

Client-side routing: React Router intercepts link clicks, changes the URL, and renders the matching component without reloading. * is the catch-all 404 route.

06

Visual Layering — How Glass Floats Over Video

Pure CSS stacking with z-index. The video and overlay are position: fixed so they stay put while content scrolls. Glassmorphism = semi-transparent background + backdrop-filter: blur() + a 1px translucent border + soft shadow.

z-index −10 Video (flower.mp4) Fills viewport, furthest back. Fixed position.
z-index −1 Dark Scrim Overlay Keeps text readable over the moving video.
z-index 0–2 Page Content Glass cards, text. Video diffuses through each panel.
z-index 3 Particle Canvas Drifting dots. Landing page only.
z-index 50 Navbar Always on top across all pages.
z-index 60 "▶ Play background" button Landing only, shown if autoplay is blocked.

08

The Flower / Background Video Subsystem

The reference used a scroll-scrubbed video. After iterating (including a procedural 3D flower), the correct answer was: the flower IS the video, so use the exact clip and autoplay it on a loop.

Why self-hosted in public/? The clip was originally a remote CDN URL, but the cloud sandbox had no outbound internet and couldn't download it. It was downloaded manually in a terminal (Invoke-WebRequest) into public/, and the app now serves it same-origin at /flower.mp4. This turned out to be the better architecture anyway — not just a workaround.

Why self-hosting is the right architecture:

Same-origin → no CORS dependency, no cross-origin throttling
No external dependency → the CDN link can't expire or rate-limit
Vite bundles public/flower.mp4 into dist/ so the build is self-contained

Robust playback is handled by videoSource.js (autoplayLoop):

Browsers only autoplay muted video → force muted as property AND attribute (React is unreliable about reflecting muted)
A single play() can lose a race during render → retry on timers + media-ready events
Browsers pause video in hidden tabs → resume on visibilitychange
If autoplay is still blocked → start on first scroll/click/tap, show a "▶ Play background" button as manual fallback
The real bug we fixed: the video loaded and decoded fine but stayed frozen. Root cause was prefers-reduced-motion — the OS (Windows "animation effects" off) reports it, and the code was honoring it by pausing the video. Since the moving flower is the core experience (silent, non-interactive), the fix was to always autoplay. Diagnosis was done by inspecting the live element's readyState, error, currentTime vs. real time, visibilityState, and the reduced-motion media query — not by guessing.
09

Styling Architecture

Two CSS files, deliberately separated:

src/index.css — the global design system.
A :root block of CSS custom properties (design tokens): backgrounds, text colors, three accents, glass background/border/blur, radius, max width. Everything references these tokens, so re-theming means changing a few variables. Also defines reusable blocks: .glass, .container, .btn, .navbar, .feature-grid, form fields, etc.
src/pages/Landing.css — scoped to the landing only.
Every rule is prefixed with .veldara-page so the exact-replica styles can't leak into the glass pages. This is deliberate scope isolation — same principle as CSS Modules, done manually.
10

Form + Validation Architecture

Strict separation of concerns — the logic and the UI are split into two separate files:

utils/contactValidation.js — a pure validate(values) function (no React, no DOM) returning an errors object. Pure = trivially testable and reusable anywhere.
components/ContactForm.jsx — UI + state. Tracks values, runs validate() on submit, shows inline errors, clears each error as the user fixes it, shows success.

Client-side validation rules:

Name: required, minimum 2 characters
Email: required, valid format (regex)
Message: required, minimum 10 characters

The form uses noValidate so our custom logic runs, not the browser's native validation UI.

Linting — ESLint (Flat Config)

Linting = static analysis that reads code without running it and flags bugs and rule violations. Think of it as a spell-checker for code logic and syntax. ESLint 9 introduces the flat config format — a single eslint.config.js that exports an array of config objects applied in order.

ignores block
Skips dist/, node_modules/, and coverage/. ESLint never looks at generated or vendor code.
@eslint/js recommended
Baseline JS correctness rules — catches undefined variables, unreachable code, bad equality, etc.
eslint-plugin-react
React-specific best practices. The jsx-runtime preset means you don't need to import React in every file (React 17+ feature).
eslint-plugin-react-hooks
Enforces the Rules of Hooks — catches effect and re-render bugs caused by wrong hook usage (e.g. hooks inside conditions).
eslint-plugin-react-refresh
Hot-reload safety. Warns when a module exports something that would break Vite's fast refresh.
Test-file override
A separate config block adds Vitest globals (describe, it, expect, vi) so ESLint doesn't flag them as undefined.
Intentional overrides: prop-types is off (we use TypeScript-style inference), react-refresh/only-export-components is a warning (not error), and no-unknown-property is off (to allow custom HTML attributes in JSX). 
// Run linting:
npm run lint       # report only
npm run lint:fix   # auto-fix what can be fixed

Prettier — and How It Coexists With ESLint

Prettier is an opinionated formatter (style only, not bugs). ESLint can also enforce style, which would conflict. The bridge is eslint-config-prettier — placed last in the ESLint config array, it switches off every ESLint stylistic rule that Prettier already handles.

Division of labor: Prettier owns formatting. ESLint owns code quality. They never fight.
OptionValueEffect
semitrueAlways add semicolons at end of statements
singleQuotetrueUse ' instead of " for strings
trailingComma"es5"Trailing commas where valid in ES5 (objects, arrays)
printWidth80Wrap lines longer than 80 characters
tabWidth22 spaces per indentation level
arrowParens"always"Always parenthesize arrow function params: (x) => x

.prettierignore keeps Prettier off node_modules/ and dist/.

// Run formatting:
npm run format         # rewrite all files
npm run format:check   # verify only (CI-safe)

Vite-native, extremely fast. Same config file as the build tool.

A browser DOM simulated in Node. Components render without a real browser.

Readable DOM matchers: toBeInTheDocument(), toBeVisible(), etc.

Demo Q&A — Likely Client Questions

Why React?
Component reuse, huge ecosystem, the SPA standard. React lets you build the UI as composable pieces — a Navbar, a VideoBackground, a ContactForm — each independently testable and reusable anywhere in the app.
Why Vite instead of Create React App?
CRA is officially deprecated. Vite is dramatically faster at both dev startup and production build. It uses native ES modules during development so there's nothing to compile on save — changes appear instantly.
How is this a single-page application?
The browser loads index.html exactly once. React Router intercepts every link click, changes the URL in the address bar, and tells React which component to render — all without a server request. The server never sees the navigation, the page never reloads.
How is the flower video done?
It's a video file, flower.mp4, self-hosted in the public/ folder. The development environment (cloud sandbox) had no outbound internet, so the file was downloaded manually via Invoke-WebRequest in the terminal and placed in public/. The app serves it same-origin — no CORS issues, no CDN dependency that could expire. videoSource.js handles reliable autoplay with retries and fallbacks.
Why did the video freeze initially?
The OS had "animation effects" turned off, which causes the browser to report prefers-reduced-motion: reduce. The code was correctly honoring that setting by pausing the video — a responsible default. But since the moving flower is the entire visual identity of the app (silent, non-interactive), we made the background always play regardless. The diagnosis was done by reading the video element's readyState, currentTime, and the reduced-motion query directly in DevTools console.
What does the code quality setup look like?
Three layers. ESLint catches correctness issues — undefined variables, broken hook rules, bad patterns. Prettier enforces consistent formatting — quotes, semicolons, indentation. eslint-config-prettier bridges them so they don't conflict. Vitest runs 8 unit tests covering both the pure validation logic and the form component's behavior. All three run as npm scripts and all must pass before a commit.
What is glassmorphism and how did you implement it?
Glassmorphism is a UI style where panels appear to be frosted glass — you can see the background through them, blurred. Implemented with three CSS properties: a semi-transparent background (rgba), backdrop-filter: blur() which blurs whatever's behind the element, and a thin translucent border. Because the background is a live video, the blur diffuses the moving flowers through each panel in real time.
How does the form validation work?
The validation logic is a pure JavaScript function in contactValidation.js — no React, no DOM. It takes the form values and returns an errors object. The form component calls it on submit and displays errors inline. As the user types, each field's error clears immediately. This separation means the validation logic is independently testable and reusable in any other form without touching the UI code.

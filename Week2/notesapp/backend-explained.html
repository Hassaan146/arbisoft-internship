Notes App · Backend

How the backend works

A conceptual map of the FastAPI backend — what each part is for and how a single request travels through it. No code, just the ideas.

The one big idea

The backend is a kitchen with stations. Every request is an order that passes through stations one by one — each does a single job and hands off to the next. Splitting the work this way keeps every piece small, testable, and safe to change on its own.

The journey of one request

Example: “Create a note for user 5.”

Router
The waiter. Receives the request at a URL and hands the incoming data to the bouncer for checking.
↓
Schema
The bouncer. Validates the data — no blank title, no over-long text. Bad input is turned away immediately.
↓
Service
The manager. Applies the rules: does user 5 exist? Does this note belong to them? Then decides to save.
↓
Repository
The librarian. The only station allowed to talk to the database. It just fetches and stores — no decisions.
↓
Model & DB
The shelves. The note is written as a real database row, then travels back out — shaped into clean JSON by a schema.

Each station, and what its functions do

What things are

Models models.py

  • User — a person who owns notes.
  • Note — a single note that always belongs to one user.
  • Defines the core link: one user → many notes, and a note can never exist without an owner.
The bouncer

Schemas schemas.py

  • Trim & reject blanks — clean the title, refuse empty ones.
  • Note shapes — separate forms for create, edit, and read.
  • User-with-first-note — creating a user requires a first note, which is how “every user has at least one note” is guaranteed at the door.
The librarians

Repositories repositories/

  • Find — by id, or by username.
  • List — a user’s notes, one page at a time.
  • Count — how many notes a user has (cheaply).
  • Save / Remove — write or delete rows. No rules here.
The brain

Services services/

  • Create user — block duplicate names; make user + first note together.
  • Ownership guard — a note not owned by you is treated as “not found.”
  • CRUD — create, read, update, delete notes.
  • Last-note rule — refuse to delete a user’s final note.
The waiters

Routers routers/

  • Define the URLs — /users, /users/{id}/notes.
  • Carry the order — call the manager, return the reply.
  • Hold no logic — deliberately thin.
The building

App setup main.py

  • Assembles all the stations into one app.
  • House rules — CORS, rate limiting, security headers.
  • Error translator — turns internal errors into HTTP codes.
The plumbing

Support files

  • config.py — settings from the environment.
  • database.py — opens/closes a DB session per request.
  • dependencies.py — hands each waiter a ready manager.
  • exceptions.py — the vocabulary of errors.
Confidence

Tests tests/

  • Prove CRUD works end to end.
  • Prove validation rejects bad input.
  • Prove one user cannot reach another’s notes.

How the app answers back

Every outcome maps to a standard HTTP status code, so any client knows exactly what happened.

201A note or user was created.
200A read or update succeeded.
204Something was deleted — nothing to return.
404Not found — or not yours to see.
409That username is already taken.
422The input broke a rule (blank title, deleting the last note).
429Too many requests — please slow down.
